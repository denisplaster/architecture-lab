03

Tour the template

0:10–0:18 · 8 min

Templates add two kinds of files: the ones every project needs, and samples that prove the template works. For each file, decide what you would do with it, then check your answers.

Teacher notes
Say
  • Our job is to tell the needed files from the samples.
  • launchSettings.json is local only; appsettings.json ships everywhere. package-lock.json gets committed; node_modules, bin and obj never do.
Ask
Which of these files would break the app if you deleted it? (Program.cs, the .csproj, index.html, main.tsx, package.json.)
If you're behind
Cover only Program.cs, launchSettings.json, App.tsx and vite.config.ts. Students read the rest after class.

Repository root

  • .gitignore

    Lists the files Git should never commit.

    keep. bin/, obj/, node_modules/ and editor settings must stay out of the repository. Created by dotnet new gitignore.

  • ClassroomApp.slnx

    The solution file: which .NET projects belong together.

    keep. dotnet build and Visual Studio use it to build and open every project at once. .slnx is the XML format .NET 10 creates by default.

API · src/ClassroomApp.Api

  • ClassroomApp.Api.csproj

    The project file: framework, compiler settings, NuGet packages.

    keep. Without it there is no project. It targets net10.0, turns on nullable reference types and references Microsoft.AspNetCore.OpenApi.

  • Program.cs

    The entry point: registers services and sets up the request pipeline.

    change. Keep the setup, remove the WeatherForecast sample endpoint and its record.

  • ClassroomApp.Api.http

    Requests you can send from the editor with one click.

    change. Useful, but it points at the sample /weatherforecast route.

  • Properties/launchSettings.json

    Settings for running the app on your machine: ports and environment.

    change. Production never reads it, and the template picked a random port. We pin it to 5080 so everyone's matches.

  • appsettings.json, appsettings.Development.json

    Configuration for every environment, plus overrides for Development.

    keep. Logging levels now, connection strings later. Secrets don't belong in either file.

  • bin/, obj/

    Folders the build creates.

    ignore. Recreated on every build. Never edit or commit them; .gitignore already skips them.

React · src/web

  • package.json

    Scripts and dependencies for the React app.

    keep. npm run dev, build, lint and preview come from here, and so do React 19, Vite 8, TypeScript and Oxlint.

  • package-lock.json

    The exact version of every installed package.

    keep. Commit it, so every machine installs exactly the same packages.

  • node_modules/

    The installed packages themselves.

    ignore. npm install recreates it. Never commit it.

  • index.html

    The single HTML page the app loads into.

    change. Vite starts from it and loads /src/main.tsx, so it stays. Only the title changes.

  • vite.config.ts

    Settings for Vite's dev server and build.

    change. We add a proxy so /api requests reach the .NET API.

  • tsconfig.json, tsconfig.app.json, tsconfig.node.json

    TypeScript settings.

    keep. One file for code that runs in the browser, one for config that runs in Node, and one that ties them together.

  • .oxlintrc.json

    Linter rules.

    keep. Oxlint is the fast linter Vite now uses by default instead of ESLint. Run it with npm run lint.

  • .gitignore

    Node-specific files Git should skip.

    keep. Covers node_modules, dist and log files inside this folder.

  • README.md

    Notes from the template about Vite plugins.

    delete. Your project gets its own README at the repository root.

  • public/favicon.svg

    The icon in the browser tab.

    keep. Files in public/ are served as they are. Keep it until you have a logo of your own.

  • public/icons.svg

    A sheet of social-media icons.

    delete. Only the demo page used it.

  • src/main.tsx

    Starts React in the page.

    keep. It finds the #root element and renders <App /> inside StrictMode.

  • src/App.tsx

    The page you see when you run the app.

    change. It is a demo with a counter, logos and links. We replace it with our own.

  • src/App.css

    Styles for App.tsx.

    delete. They only style the demo.

  • src/index.css

    Global styles.

    change. The template's are tuned for the demo, so they get a small replacement.

  • src/assets/

    Images: hero.png, react.svg, vite.svg.

    delete. Only the demo used them.

Organize by feature and make the boundaries real. Each feature gets a folder with everything it needs and one public entry file; shared code moves into its own folder.

Organize by feature and make the boundaries real. The boundaries become separate projects, and the compiler enforces which project may reference which.

Teacher notes
Say
  • Large-project rule: organize by feature and make the boundaries real.
  • Live demo for .NET: add using ClassroomApp.Infrastructure.Courses; to the top of GetCourses.cs and build. The compiler refuses with CS0234, because Application doesn't reference Infrastructure. The boundary is enforced, not just agreed.
  • In React nothing stops a deep import yet. Real projects add a lint rule so the boundary survives new teammates.
Point out
CoursesPage.tsx moved without changing a line, and the unit test runs without a server or a database. Those two facts are the payoff of the large structure.
Watch for
  • git mv reports that the destination directory does not exist: the folder step was skipped.
  • A blank page or a build error about ./App.tsx: main.tsx still has the old import.
If you're behind
Students do the React half while you demo the .NET half on the projector. The .NET commands become homework, since they are all on this page.
  • Domain references nothing, so business rules never depend on a database or the web.
  • Application declares interfaces for what it needs; Infrastructure implements them. Swapping memory for EF Core changes one project.
  • Api references Application and Infrastructure, and Program.cs is the only place that connects them.
  • A feature imports from shared/, never from another feature's folders.
  • Code outside a feature imports only its index.ts. shared/ never imports from features/ or app/.

Same features, two structures. Look at what moved, then decide when you would switch.

Teacher notes
Say
  • Start small. Switch when it hurts, and use the signals on screen to notice when it does.
  • Both branches do exactly the same thing. Structure changed where code lives and who may depend on whom, not what the app does.
Ask
Exit ticket: three questions on paper or in the class chat. Collect them at the door.

  1. A line like src/web/src/{ => app}/App.tsx means the file moved. Lines with + and - counts are files whose contents changed.

    PowerShellTerminal
    git diff --stat -M small large

Switch from small to large when…

  • More than one team, or more than four or five people, work in the same app.
  • A folder such as components/ or Services/ passes 15 to 20 files.
  • One feature change touches four or more folders.
  • People keep editing the same files and hitting merge conflicts.
  • You want to test business rules without a database or a browser.

Until then, stay small: fewer projects and folders means faster changes.

Exit ticket

  1. Name one file you deleted and one you changed. Why each?
    Answer: Deleted: App.css, src/assets, icons.svg or the web README, because they only served the demo. Changed: Program.cs (removed WeatherForecast), launchSettings.json (fixed port) or App.tsx (replaced the demo). Any pair with a sound reason counts.
  2. Two developers, six screens, one API. Small structure or large, and why?
    Answer: Small. The large structure's extra projects and folders cost time on every change, and one small team has no boundaries to protect yet.
  3. In the large React structure, features/students needs CourseCard. May it import features/courses/components/CourseCard?
    Answer: No. Import it from features/courses, the feature's index.ts, if courses exports it. If several features need it, move it to shared/ui.
  4. Why does GetCourses depend on ICourseRepository instead of InMemoryCourseRepository?
    Answer: So Application never references Infrastructure. You can swap in EF Core, or a fake in a test, without touching the use case.
Troubleshooting
dotnet or node is not recognized
Install it, then close and reopen the terminal so it picks up the new PATH.
code is not recognized on a Mac
In VS Code open the Command Palette and run Shell Command: Install 'code' command in PATH. Or use File, Open Folder.
PowerShell: running scripts is disabled on this system
Run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once, then reopen the terminal.
Windows Terminal warns about pasting several lines
Choose Paste anyway. The lines run one after another.
dotnet new sln made ClassroomApp.sln, not .slnx
Your SDK is older than .NET 10. Everything still works; check dotnet --version.
Vite asks which linter to use, or whether to install and start now
A flag got lost while copying. Choose Oxlint, then No.
Git says: Please tell me who you are
Run git config --global user.name "Your Name" and git config --global user.email "you@example.com", then commit again.
'Course' is a type and must be imported using a type-only import
Write import type { Course }. The template turns on verbatimModuleSyntax.
Failed to determine the https port for redirect
Expected on the http profile: HTTPS redirection has no HTTPS port to send you to locally. It is a warning, not an error.
The page says Could not load courses: 502 Bad Gateway
The API isn't running. Start it in a second terminal with dotnet run --project src/ClassroomApp.Api.
Port 5080 is already in use
Pick another port in launchSettings.json and use the same number in vite.config.ts.
git mv: destination directory does not exist
Run the folder step first, then repeat the moves.
